# 小猫搬金条项目架构规范

## 1. 目标

将项目整理为可长期维护、可测试、可发布，并能逐步迁移到微信原生小程序的产品工程。整理过程必须保持现有 GitHub Pages 公开入口兼容，不直接改动生产数据库。

## 2. 架构原则

- **稳定入口优先**：当前公开 URL 在完成兼容验证前不得删除或改变。
- **应用与业务分离**：页面负责展示和交互；业务规则放在独立模块；数据访问通过适配层完成。
- **单一事实来源**：计时计算、工资计算、账户状态和游戏规则避免在多个页面复制维护。
- **平台适配隔离**：Web 与未来微信小程序可以有不同 UI/平台适配器，但共享经过验证的纯业务逻辑。
- **后端权威**：金币、购买、奖励、结算和用户数据权限由服务端决定，客户端不持有 service_role 等秘密。
- **渐进式迁移**：每个阶段独立提交、运行测试、检查页面入口，不进行一次性大爆炸式重写。
- **可追溯**：历史版本保留来源和用途；不确定用途的文件先归档标记，不直接删除。
- **环境隔离**：开发、测试、生产配置和数据边界明确。

## 4. 当前版本分类

- 当前正式网页：`v5.4.1.html` 与 `ledger54-5.4.1.html`。
- 内测网页：`beta-v5.5.html`，不得自动替换正式入口。
- 游戏页面：`cat-workshop.html`，当前依赖父页面提供 RPC bridge，不应被描述为独立可运行页面。
- 历史页面：`v5.1.html`、`v5.2.html`、`v5.3.html`、`v5.4.html` 及旧账本页面。
- 自动化脚本和工作流属于工程基础设施，不属于应用运行时代码。
- Supabase migrations 是数据库变更历史，必须保持时间顺序与实际生产数据库状态一致。

## 5. 路径迁移规则

GitHub Pages 当前通过仓库根目录提供静态站点。移动页面前必须：

1. 列出所有内部链接、脚本、样式、manifest、图标和版本检查 URL。
2. 确认 GitHub Pages 发布目录和 Actions 发布脚本支持新目录。
3. 对现有公开 URL 提供兼容入口或明确的重定向策略。
4. 验证相对路径、PWA scope、缓存、localStorage 同源行为和页面间导航。
5. 在预览分支完成端到端验证后才合并。

不允许只移动文件而不处理上述依赖。

## 6. 代码分层约定

- **pages**：页面结构、事件绑定、视图状态；不重复实现核心业务规则。
- **components**：可复用 UI 单元，不直接拥有跨页面业务状态。
- **domain**：纯函数和领域规则，不依赖 DOM、window、微信 API 或 Supabase SDK。
- **application**：组织用例，例如开始工作、结束工作、导入备份、购买商品。
- **infrastructure/adapters**：浏览器存储、Supabase RPC、微信 API 等平台实现。
- **contracts**：请求/响应结构、字段校验和版本化数据契约。
- **tests**：单元、集成、回归和端到端测试分别归类。

## 7. 质量门禁

每次重构至少执行：

- 静态语法与代码审计。
- 计时与工资计算回归测试。
- 账本读写与账号隔离测试。
- 游戏 RPC 桥接和服务端结算测试。
- Supabase migration 静态审计及数据库行为测试。
- GitHub Pages 入口、内部链接和资源路径检查。

CI 通过不等于真实微信环境或生产端到端测试通过；发布说明必须明确测试范围。

## 8. 禁止事项

- 不直接在生产数据库试跑未经核对的 migration。
- 不把 service_role、数据库密码或其他秘密提交到仓库。
- 不在未验证兼容性前删除旧版本或更改生产入口。
- 不把测试文件、临时预览文件误当作正式发布产物。
- 不把网页代码简单改名为小程序代码；微信小程序需要独立平台适配与审核准备。
