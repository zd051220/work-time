# 发布回滚与故障处置

## 1. 目标与原则

回滚用于尽快恢复可用服务，但必须区分静态网页代码、客户端本地数据、云端数据和数据库结构。恢复网页文件不会自动恢复或修复数据库状态。

优先保护用户数据；任何可能删除、覆盖或重置用户数据的操作，都必须先评估并取得明确授权。

## 2. 触发条件

可考虑回滚或紧急修复的情况包括：

- 核心计时或工资计算出现严重错误。
- 账本无法读取/保存，或出现数据覆盖风险。
- 账号隔离或权限控制出现异常。
- 正式入口、关键资源或更新机制导致大面积不可用。
- 新版本引入无法通过配置规避的严重故障。

普通视觉问题或非阻断缺陷应先评估热修复，不必自动回滚整个版本。

## 3. 静态网页回滚步骤

1. 确认当前生产版本、故障表现和影响范围。
2. 找到最近一个已验证的稳定 Git Tag/Release。
3. 检查该版本对应的提交、页面入口和资源依赖。
4. 通过受审查的 hotfix/回滚 PR 恢复已知稳定代码；避免直接重写公共历史。
5. 运行与故障相关的回归测试。
6. 部署后等待 Pages 工作流成功。
7. 在线验证正式入口、核心流程和版本提示。
8. 发布故障说明，记录恢复版本、时间、原因和后续措施。

不得仅凭“某个旧 HTML 文件还在仓库里”就认定它是可回滚的完整版本；必须核对同一提交中的依赖、配置和数据兼容性。

## 4. 数据库与云端数据

- 不要把网页 Git 回滚等同于数据库回滚。
- 执行过的数据库 migration 不得未经评估直接反向删除。
- 对数据库故障优先制定向前修复方案；必要时依据经过验证的备份恢复流程处理。
- 在任何恢复操作前确认备份时间点、恢复范围、潜在数据丢失量和用户影响。
- 不在没有用户授权和明确恢复方案时修改生产数据库或用户存档。

## 5. 本地数据与版本兼容

如果新版本改变 localStorage、IndexedDB、导入导出结构或云端同步契约：

1. 发布前必须准备迁移与兼容策略。
2. 优先采用可重复执行、可检测版本的迁移。
3. 不在用户计时、录入账目或同步过程中强制刷新。
4. 若旧版本无法读取新数据，必须先明确阻止不安全降级，或提供经过验证的兼容转换。
5. 回滚后抽样验证历史数据仍可读取；不得仅以页面能打开作为恢复成功标准。

## 6. 事故记录

每次生产回滚或紧急修复记录：

- 受影响版本、平台和用户流程。
- 发现时间、恢复时间与影响范围。
- 触发原因及根因（若已确认）。
- 回滚/修复提交与部署记录。
- 数据是否受影响、是否恢复及验证证据。
- 后续预防措施。

没有证据确认的根因应标记为“待调查”，不要猜测。
