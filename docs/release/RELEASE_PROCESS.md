# 正式发布流程

本流程适用于「小猫搬金条」Stable 正式版。DEV、Alpha、Beta 和 RC 可按风险裁剪检查，但必须清楚标记渠道，不能冒充正式版。

## 1. 发布前准备

1. 明确发布目标、用户可见变化、影响模块和版本号。
2. 确认版本号符合 `docs/release/VERSIONING.md`。
3. 检查当前 `main` 是否干净、是否包含预期提交。
4. 确认所有新增依赖、静态资源、页面路径和运行时配置。
5. 检查是否涉及数据格式、账号隔离、Supabase RPC 或数据库迁移。
6. 更新 `CHANGELOG.md`，准备面向用户的中文更新公告。

## 2. 分支与 Pull Request

建议分支命名：

- `feature/<short-name>`：新功能。
- `bugfix/<short-name>`：一般缺陷修复。
- `release/<version>`：发布准备与冻结。
- `hotfix/<version>-<short-name>`：生产紧急修复。

所有改动通过 Pull Request 进入 `main`。PR 必须说明变更范围、风险、测试证据、数据迁移影响及回滚方式。禁止未经审查直接向生产分支推送发布内容。

分支保护、必需审查人数和必需状态检查应在 GitHub 仓库设置中启用；本文件本身不代表这些设置已经启用。

## 3. 自动化与人工验收

正式发布至少需要：

- 静态代码审计与语法检查通过。
- 计时、工资计算和跨午夜等核心回归通过。
- 账本保存、读取、导入导出及用户数据隔离检查通过。
- 猫咪游戏 RPC 桥接、购买、奖励和结算检查通过（涉及游戏改动时）。
- Supabase SQL/migration 静态审计通过；若涉及数据库变更，先核对生产 schema 与迁移历史。
- 页面入口、资源路径、版本检查、缓存与导航验证通过。
- 在目标设备/浏览器进行必要的人工验收。
- 检查 CI 覆盖范围；CI 未覆盖的项目必须明确记录为未验证，不能宣称全部通过。

出现核心计时、工资、账本或数据权限阻断问题时，不得发布 Stable。

## 4. RC 与冻结

1. 从最新且已审核的代码创建 `release/<version>` 分支。
2. 生成 `<version>-rc.1` 候选版本并执行完整回归。
3. RC 阶段原则上只接受阻断问题修复、发布说明修订和必要的发布配置修正。
4. 每次 RC 代码发生变化，递增候选序号并重新执行受影响测试。
5. 验收通过后确定正式发布提交。

## 5. 正式发布

1. 确认最终提交已合并至 `main`。
2. 创建指向该提交的不可变 Git Tag：`v<version>`。
3. 基于该 Tag 创建 GitHub Release，填写更新内容、修复、已知问题、兼容性和测试范围。
4. 更新运行时版本配置（例如 `version.json`）前，先确认版本检测器兼容性及缓存策略。
5. 触发 GitHub Pages 部署；等待部署工作流成功。
6. 访问正式网址，核对实际页面版本、入口跳转、资源加载和更新提示。
7. 完成线上冒烟测试后，才将发布状态记为已上线。

GitHub PR 合并成功不等于 Pages 部署成功；Pages 工作流成功也不自动证明所有用户路径均已验收。

## 6. 发布公告

每个 Stable 版本都应在 `CHANGELOG.md` 和 GitHub Release 中记录：

- 版本号与发布日期。
- 新增功能。
- 改进与修复。
- 已知问题。
- 数据/兼容性影响。
- 测试范围及未覆盖项目。
- 如需用户操作，明确给出步骤。

网页内公告应与 GitHub Release 内容一致，并保留历史公告。

## 7. 发布后监控

发布后检查：

- 页面是否可访问、入口是否正确。
- 计时和工资计算是否正常。
- 账本是否能正常读取和保存。
- 更新检测是否正确识别 Stable 版本。
- 是否出现明显错误反馈或数据异常。

如发现严重问题，按 `docs/release/ROLLBACK.md` 处理，并记录事件。

## 8. 当前工作流限制

当前仓库的 `.github/workflows/release-manual.yml` 是一个根目录单文件手动发布流程，会直接向 `main` 推送，不是完整的 Tag/Release 发布流水线。完成工作流重构、分支保护和路径兼容验证之前，不应将它视为本规范定义的正式发布入口，也不应通过它发布多文件版本。
