# 版本号与发布渠道规范

本文件定义「小猫搬金条」的产品版本规则。适用于网页端及未来的平台客户端；平台构建号另行记录，不替代产品版本号。

## 1. 版本号格式

正式版本采用语义化版本（SemVer）：

`MAJOR.MINOR.PATCH`，例如 `5.6.0`。

- **MAJOR（主版本）**：出现不兼容变更、重大架构迁移或需要用户采取明显迁移步骤时递增；递增后 MINOR 和 PATCH 归零。
- **MINOR（次版本）**：以向后兼容方式增加面向用户的功能；递增后 PATCH 归零。
- **PATCH（修订版本）**：向后兼容的问题修复、安全修复或小幅稳定性改进。
- 仅重构且不改变用户可见行为或兼容契约时，不自动增加 MAJOR；根据是否包含可见功能或修复决定是否发布。

正式版本号不带前缀时为 `5.6.0`；Git Tag 统一使用 `v5.6.0`。

## 2. 预发布版本

预发布版本在正式版本号后添加连字符标识：

- `5.6.0-dev.1`：开发构建，仅供开发验证。
- `5.6.0-alpha.1`：早期内测，功能可能不完整。
- `5.6.0-beta.1`：功能基本完整，供更广泛测试。
- `5.6.0-rc.1`：Release Candidate，候选正式版本。

同一阶段每次产生新的候选构建时递增序号。预发布版本不得被误标为 Stable，也不得覆盖正式版本下载地址。SemVer 规定预发布版本低于对应的正式版本。

**与正式发布工作流的边界：** `-dev.N` 仅用于开发阶段标识，不进入 `.github/workflows/formal-release.yml` 的正式发布流程，也不创建正式 Tag 或 GitHub Release。当前正式发布工作流只接受 `-alpha.N`、`-beta.N`、`-rc.N` 三类预发布后缀；Stable 只接受不带后缀的三段式版本号。DEV 构建如需自动化，应使用独立的开发构建流程，不得复用 Stable 发布入口。

## 3. 发布渠道

| 渠道 | 用途 | 面向对象 |
| --- | --- | --- |
| DEV | 日常开发构建，可能随时变化 | 开发者 |
| Alpha | 早期功能与技术验证 | 内部测试 |
| Beta | 较完整功能的体验与反馈 | 明确参与测试的用户 |
| RC | 功能冻结后的发布验收 | 发布验收人员 |
| Stable | 通过发布门禁的正式版本 | 普通用户 |
| LTS | 明确指定维护周期的稳定维护分支 | 需要长期稳定的用户 |

渠道是发布状态，不是额外的版本数字。猫咪游戏模块可以单独标注 Beta；这不自动改变工作计时和工资账本主产品的 Stable 状态。

## 4. 当前版本的过渡规则

仓库当前线上版本标识为 `5.5`，`version.json` 也仍使用这一旧格式。为避免未经验证地影响现有更新检测逻辑：

1. 暂将当前生产基线按语义化版本规划视为 **5.5.0 的过渡基线**。
2. 本次文档规范化不修改 `version.json`、页面入口或线上代码。
3. 在审查版本比较、缓存策略和更新提示兼容性之前，不创建或宣称已创建 `v5.5.0` 正式 Tag。
4. 从下一次正式发布开始，采用完整三段式版本号；如下一次发布是新增功能，版本为 `5.6.0`；如先修复当前版本问题，则为 `5.5.1`。
5. 任何版本 Tag 必须指向实际验收并发布的提交，不能为了补齐命名而给历史提交追溯性贴标签。

## 5. 版本来源与唯一事实来源

- 产品版本：正式发布版本及预发布版本号。
- Git Tag：某次发布源代码提交的不可变标识。
- GitHub Release：该 Tag 对应的发布说明、资产和已知问题。
- `version.json`：网页运行时更新检测使用的配置。它属于运行时发布配置，必须与实际 Stable 版本一致；在完成兼容性验证前不擅自改变其字段结构。
- 平台构建号：未来小程序审核版本、构建流水号等平台专属信息，单独记录，不与产品版本混用。

## 6. LTS 政策

LTS 不是自动产生的版本类型。只有在明确指定维护负责人、支持范围、结束日期和安全修复流程后，才可宣布某个版本为 LTS。未作正式声明的历史版本不承诺持续维护。

## 7. 版本变更示例

- `5.5.0 → 5.5.1`：修复工资计算边界问题。
- `5.5.1 → 5.6.0`：新增向后兼容的统计功能。
- `5.6.0 → 6.0.0`：数据契约或用户操作流程发生不兼容的重大变化。
- `5.6.0-beta.1 → 5.6.0-beta.2`：测试阶段修复问题并重新发布候选构建。
- `5.6.0-rc.1 → 5.6.0`：仅当验收通过且正式发布代码与 RC 完全一致时，正式版可使用同一提交；否则先生成新的 RC。

## 8. 不允许的做法

- 不因每次代码提交或每次部署就增加产品版本号。
- 不把 Beta/RC 标记为 Stable。
- 不移动或重写已公开使用的正式 Tag。
- 不在未核对数据库迁移和数据兼容性的情况下宣称可安全回滚。
- 不将网页版本号、小程序审核版本号和构建流水号混为一谈。
